01 / ARCHITECTURE

One authoritative write path

Data flow: browser request → API validation/authentication → domain rule → SQL transaction → response. Course catalogue, offerings, enrollments and academic records use PostgreSQL as the source of truth.
Engineering boundary: cache, rate limiter, hash-ring and telemetry experiments are process-local. The prototype does not claim distributed coordination or PostgreSQL sharding.

04 / SYSTEM DESIGN COMPONENTS

Concepts made observable

Rate limiterToken-bucket admission control; overload requests can return HTTP 429.
Sharding simulationRoutes synthetic key/value records to shard buckets; it does not shard PostgreSQL.
Consistent hashingRing-based key routing and node-change movement experiment; no automatic data migration.
Key-value cacheTTL/LRU cache for autocomplete, with observable MISS/HIT behavior.
Unique IDsSnowflake-style 64-bit IDs; API serializes IDs as strings to avoid JavaScript precision loss.
Short URLCreate and redirect through the application’s persistent short-link path.
Bounded crawlerURL frontier and safety limits are demonstrable; live public crawling remains unverified.
AutocompletePrefix-based course suggestions with cache-backed repeated lookup.

Paced load baseline9.84 requests/s in the fresh local rerun.
Separate overload experiment: 40,372 of 48,459 unpaced samples returned HTTP 429 (83.32%); 8,081 returned HTTP 200 and 6 timed out. Failed samples include transport timeouts, so this is admission-control evidence—not baseline capacity.

Local single-laptop measurements; not production capacity certification. A second paced run had p95 20 ms, so repeat runs are needed for stronger claims.
